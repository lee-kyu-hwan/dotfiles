### 심사 지적을 확인하다 새로 발견한 사실 오류

READY-03 이 "현재 `codex exec --help` 의 승인 자동화·hook trust·rules 무시·쓰기 경로 확장 옵션"을 개별 판정하라고 요구해 실제로 `codex exec --help` 를 실행했다. 그 결과 **R1.4 가 열거하던 `--full-auto` 와 `--yolo` 는 codex-cli 0.153.4 의 `exec` 에 존재하지 않는다**는 것을 확인했다. 실재하는 우회·확장 옵션은 `--skip-git-repo-check`, `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-bypass-hook-trust`, `--approve-for-me`, `--ignore-rules`, `--ignore-user-config`, `--add-dir` 일곱이다. R1.4 를 그 일곱과 CLI 버전으로 다시 쓰고, AC-4·AC-92 와 § Security and risk 를 함께 맞췄다. `SKILL.md` 의 기존 금지 문언은 R9.6·AC-78 때문에 그대로 둔다.

4. R1.4 의 목록 교체가 AC-4 의 판정 대상과 AC-92 의 열거를 동시에 바꿔 세 곳이 어긋나지 않는다. `SKILL.md` Safety rules 를 건드리지 않으므로 AC-78·CMD-4 와도 충돌하지 않는다.

## attempt 3 개정 (readiness READY-03·11 + 사용자 설계 결정)

개정 전 647행 / AC 92 → 개정 후 659행 / 요구사항 67 / AC 93 / 추적표 67행.

attempt 3 은 **score 93, blockers 0, Critical/High 0** 이었고 체크리스트는 C1~C7 pass, C8 만 fail 이었다. 심사 스스로 "Critical/High 가 0 인 반복 한도 소진 경로이므로 추가 readiness 시도 없이 ARBITRATION 으로 진행하라"고 판정했다. 설계한 탈출 경로가 그대로 작동했다.

- **READY-11 (Medium) — 내 사실 단정이 틀렸다.** attempt 2 개정에서 `codex exec --help` 출력만 보고 "`--yolo` 는 존재하지 않는다"고 단정했다. 실제로는 `codex exec --yolo --version` 이 종료 코드 0 과 `codex-cli-exec 0.153.4` 를 출력한다. `--help` 에 없는 숨은 별칭이다. 반면 `--full-auto` 와 임의의 미지원 플래그는 사용법 안내를 낸다. R1.4 의 목록을 여덟 개로 고치고 `--yolo` 를 포함했으며, 목록을 `--help` 가 아니라 플래그별 수용 여부 실측으로 만들었다는 것을 § Security and risk 에 명시했다. AC-92 도 여덟 이름과 숨은 별칭 사실을 함께 요구하도록 고쳤다.
- **READY-03 (Medium) 마지막 갈래** — legacy 상태에서 첫 `record-draft-attempt` 가 `draft_attempts` 를 생성하는 조건이 AC-42·AC-89 어디에도 없었다. AC-93 을 신설하고 R6.4 행에 연결했다.

### 사용자 설계 결정 반영 — R4.5 는 fail-closed 안전장치다

"2회 소진 + Critical/High 잔존 → `NEEDS_REDESIGN`" 을 유지하되, 그것이 설계 판정이 아니라 안전장치임을 D10 에 근거와 함께 기록했다. 검토한 대안("항상 Claude 중재")을 1단계에서 제외한 근거 세 가지는 저장소에서 확인했다.

1. `schemas/review.schema.json` 의 `properties.findings.items` 에 속성 정의가 없다(빈 `properties`). readiness finding 을 upheld/overruled 로 판정할 필드가 없어 잔여 blocker 를 넘기면 fail-open 이 된다.
2. 같은 스키마의 `verdict` enum 은 `PASS`·`REVISE`·`BLOCKED` 뿐이다. 공식 리뷰가 "재설계 필요"를 표현할 값이 없다.
3. AC-31 은 전달만 판정하고 판정 자체를 보장하지 않는다.

이 계약을 만드는 일은 별도 설계 작업이므로 Non-goal 11 로 분리했다. 이 실행의 실측(High 2 → 3 → 0, 중간 증가분 2건이 개정이 만든 회귀)도 D10 에 근거로 남겼다.

### 라운드 3 심사 경로 — `codex exec` 3연속 `invocation_failed`

라운드 3 의 사전 심사를 `codex exec` 로 세 번 시도했고 세 번 다 모델 응답이 멈춰 감시자가 회수했다. Spec 자신의 R6.9 분류로 전부 `invocation_failed` 다.

|---|---|---|---|---|
| 7 | 3000s / 600s | 39 | 비어 있음 | events 600s 정지 (exit 125) |
| 8 | 2700s / 480s | 7 | 비어 있음 | events 480s 정지 (exit 125) |

세 번 모두 **분석에 들어가기 전 단계**에서 멈췄다(디제스트 확인·파일 읽기 직후). 프롬프트 크기를 8.2KB → 2.6KB 로 줄여도 같았고, attempt 5 는 5.8KB 로 성공했으므로 프롬프트 크기가 원인이라고 보기 어렵다. stderr 가 비어 있고 잔존 프로세스가 없으며 `spec.md` digest 는 세 번 모두 불변이었다. 이것이 #70 코멘트 1 의 함정 2(stdin 무한 대기)와 다른 새 실패 모드다 — stdin 은 프롬프트 파일에 고정돼 있었고 초기 이벤트가 정상적으로 흘렀다.

**사용자 결정으로 exec 경로를 중단하고 6.2.2 의 대화형 Codex 세션에 같은 체크리스트 프롬프트를 넘겨 대체 심사를 받았다**(attempt 10). 이 실행의 readiness 는 배포본 v5.0.0 이 강제하는 게이트가 아니라 자기 적용 실험이며, 상태 머신은 `record-review` 에 readiness 결과를 요구하지 않는다. 따라서 R4 의 `HOLD`/`ARBITRATION` 경로는 이 Spec 이 만들 미래 동작이지 이 실행을 묶지 않는다.

**다만 "실제로 한도가 소진됐다면 어느 경로로 갔는가" 를 기록해 둔다** — `formal_round` 3 의 시도 구간에 `outcome` 이 `recorded` 인 기록이 하나도 없으므로 R6.10 표의 **갈래 ①(무기록)** 이고, 시도가 2 이상이므로 반환값은 **`ARBITRATION`** 이다. 곧 설계대로였다면 이 산출물은 "readiness 가 유효한 결과를 내지 못했다"는 사실을 공식 리뷰 근거에 명시한 채 라운드 3 으로 진행했을 것이며, 실제 진행과 같다. 이슈 #76 의 근거로 남긴다 — **연속 `invocation_failed` 로 시도 구간이 소진되는 경우가 실측으로 존재하며, 그때 갈래 ①이 fail-open 이 아니라 합리적 탈출구로 작동한다.** 다만 그 경로가 "심사 없이 통과" 와 구별되지 않으므로, R4.4 가 요구하는 "그 사실을 공식 리뷰 근거에 명시" 가 이 경로의 유일한 안전장치라는 점도 함께 남긴다.
