## Problem and context

현재 저장소는 #111에서 `dot_local/bin/executable_ai-session`의 `select|launch`, 비밀이 아닌 schema v1 account registry, 독립 `CODEX_HOME`/`CLAUDE_CONFIG_DIR`, 실행 가능한 verifier 절대경로, 10초 timeout, strict verifier schema, credential 환경 정리, consumer account 자동 전환 금지를 구현했다. 그러나 실제 provider verifier와 역할별 launcher는 의도적으로 #103 후속으로 남아 있다(`docs/session-account-profiles.md`). 역할 문자열은 현재 선택 결과와 child 환경에 전달될 뿐 모델·effort·권한·instruction·Skill 정책을 강제하지 않는다. 현재 source와 사용자가 이미 적용한 v1 target은 `codex-dotfiles`를 별도 Codex home으로 두고 두 provider의 default를 dotfiles profile로 잡아, 이번에 확정된 실제 account topology와 일시적으로 불일치한다.

issue #103은 일반, tmux 세션, feature quality-goal, global 조율의 모델과 권한을 분리하고, `role_profile`과 #111의 `account_profile`을 직교 결합하라고 요구한다. 기준 revision에는 역할 manifest나 역할 launcher가 없고, `dot_codex/private_full_auto.config.toml`은 `on-request`/`workspace-write`의 과거 호환 설정이며 저장소 내 실행 호출처는 없다. 기존 `orchestrator` 이름은 세션 역할이고 feature 역할로 재해석할 수 없다.

`installed-cli-contract-evidence.md`에 보존한 읽기 전용 help 증거에서 Codex는 `codex-cli 0.154.0`이며 `--model`, `--profile`, `--sandbox`, `--ask-for-approval`, `-c`, `--disable`을 제공한다. Claude Code는 현재 `2.1.272`이며 `--model`, `--effort`, `--permission-mode`, 단일 값의 `--settings`, repeatable local `--plugin-dir`, `--setting-sources`, `--append-system-prompt`, `--disallowedTools`, `--strict-mcp-config`를 제공하지만 `--append-system-prompt-file`은 광고하지 않는다. network fetch인 `--plugin-url`은 launcher surface에서 금지한다. offline help는 어느 provider의 model alias도 server-side availability로 보증하지 않으므로 role matrix의 model 값은 pinned policy identifier이고 provider 거부 시 fail closed/no fallback한다. 또한 설치본의 `claude auth status --help`는 auth status와 JSON/text 출력만 광고하고 공식 usage/quota contract는 제공하지 않는다. Claude verifier는 official 미로그인 결과를 `not_logged_in`으로 보존하고, 로그인된 경우에도 usage를 추측하지 않아 `usage_unknown`을 반환한다. 실제 auth/status 또는 network probe는 이 workflow에서 금지되며 두 경우 모두 provider exec 전에 차단된다.

권위 있는 topology는 Codex consumer profile을 정확히 둘 선언하되 최초 자동 선택에는 `codex-default`(`~/.codex`) 하나만 사용하는 형태다. `codex-dotfiles`는 별도 `config_home="~/.local/share/ai-account-profiles/codex/dotfiles"`를 보존한 generic multi-account candidate지만 provider default, scope binding, task binding 어디에도 참조되지 않아 처음에는 active account가 아니다. Claude consumer account는 provider-default/unset mode의 `claude-default`와 explicit separated-home mode의 `claude-dotfiles` 정확히 둘이다. 전자는 provider가 자체 기본 위치로 다루는 `~/.claude`를 사용할 뿐 launcher가 `CLAUDE_CONFIG_DIR` 값을 내보내지 않고, 후자만 선택된 절대 synthetic/배포 경로를 명시적으로 내보낸다. `lee-kyu-hwan/dotfiles` source checkout과 모든 linked worktree만 `claude-dotfiles`를 선택하고 그 밖의 context는 `claude-default`를 선택한다. 사용자 보고에 따르면 explicit separated home은 인증뿐 아니라 user settings, hooks, permissions, plugin enablement와 plugin state도 격리하여 수동으로 시작한 세션이 정상 응답하면서도 `workmux status`에서 사라졌다. 따라서 launcher는 secret-free chezmoi-managed common settings와 role settings를 하나의 reviewed document로 합성하고 local reviewed plugin surface만 명시적으로 전달해야 한다. 네 profile을 선언하고 자동 선택에서 세 profile만 사용하는 topology와 개인 Mac의 명시적 sandbox/allowlist는 그대로다. unrestricted 권한, 실제 로그인, credential 이관, 현재 tmux pane/process 변경, #94/#95의 영구 registry·복구·worktree 생성은 포함하지 않는다.

## Goals

- Codex와 Claude에 대해 네 logical role의 모델, effort, 실제 권한, additive instruction, Skill 정책을 chezmoi source와 결정적 launcher로 제공한다.
- 기존 #111 account 선택 우선순위를 단일 source of truth로 재사용하되 schema v2의 global authorization와 post-selection exclusion, required topology contract로 two-Codex/two-Claude 선언, initial Codex default-only binding, future registry-only binding activation을 fail closed한다.
- global active leader를 하나로 제한하고 reviewer/standby의 dispatch·lease 변경 능력을 instruction뿐 아니라 실행 권한과 preflight 검증으로 제거한다.
- hostile project 설정, 잘못된 binding, verifier 오류, account 변경, leader 충돌을 provider process 실행 전에 비밀 없이 차단한다.
- Claude default/unset과 explicit separated-home mode를 strict registry schema로 구분하고, 어느 account를 선택해도 reviewed common settings·role settings·허용 local plugin과 workmux 관측성이 같은 역할 정책으로 복원되게 한다.
- 실제 인증정보나 네트워크에 의존하지 않는 fixture로 argv, env, effective policy, instruction hash, source-target render, source/linked-worktree account mapping, mixed v1/v2 deployment, 고위험 leader/account 경로를 재현한다.
- 운영자가 모델 비용·availability·보존 전제, active `codex-default`의 무이관·무재로그인, 두 dotfiles candidate의 host-local login/enrollment, Codex candidate의 registry-only activation, 실패 복구, 새 세션 적용 범위를 이해할 수 있는 문서를 제공한다.

- **R2.1** Codex role matrix는 general=`gpt-5.6-sol/medium`, orchestrator=`gpt-5.6-sol/medium`, feature-orchestrator=`gpt-5.6-sol/medium`, global-orchestrator=`gpt-6-astra/high`로 고정한다. 이 model 문자열은 offline help가 availability를 증명하지 않는 pinned policy identifier다. general은 일반 구현·조사, orchestrator는 한 tmux 작업군 조율, feature-orchestrator는 명시적 대체, global-orchestrator는 여러 세션의 우선순위·충돌·인계를 담당하며 provider model 거부는 자동 alias/provider/account fallback 없이 그 nonzero exit로 끝난다.
- **R2.2** Claude role matrix는 general=`opus[1m]/high`, orchestrator=`opus[1m]/high`, feature-orchestrator=`opus[1m]/high`, global-orchestrator=`claude-fable-5-1/medium`으로 고정한다. 이 model 문자열도 offline help가 availability를 증명하지 않는 pinned policy identifier다. global만 명시적 `--effort high` elevation을 허용하며 그 선택과 사유를 startup record에 남기고 모델 ID는 계속 pinned Fable 5.1이어야 한다. provider 거부는 자동 alias/provider/account fallback 없이 그 nonzero exit로 끝난다.

Claude required option은 지원되는 additive `--append-system-prompt`, 단일 값 `--settings`, repeatable local `--plugin-dir`이고 설치 help에 없는 `--append-system-prompt-file`을 요구하지 않는다. network fetch `--plugin-url`은 금지한다. role launcher는 range와 필수 option 중 하나라도 맞지 않으면 `blocked_cli_contract`/exit 4로 provider process 전에 차단한다. 이 Mac의 필수 release gate는 설치된 두 CLI의 실제 `--version`/`--help`만 인증·network 없이 실행하며, CLI 부재도 `not_configured`나 skip이 아니라 실패다. 이 gate의 Claude CLI compatibility 통과는 usage admission 성공을 뜻하지 않으며 별도의 `usage_unknown` operational limitation을 그대로 남긴다. cross-host portable suite는 실제 CLI 유무와 무관하게 in-range/out-of-range/missing-option fixture를 사용하고 실제 binary를 호출하지 않는다.

### 역할과 계정의 직교 결합

- **R3.1** `roles.toml`은 `version = 1` strict schema를 사용하며 provider별 CLI compatibility range/required help option, Codex·Claude untrusted benign-setting exact allowlist, trusted common/composed-settings path·version·SHA-256, reviewed local plugin path와 각 logical role의 provider, default/alternate, model, effort, permission engine/mode, instruction path/version, Skill/plugin policy ID, allowed leader mode, capability를 명시한다. 누락·추가 field, 중복 provider/role, 대상이 없는 경로, 잘못된 range/key/enum/hash 또는 role deny와 common permission/env/plugin의 충돌은 `blocked_role_schema`로 fail closed한다.
- **R3.2** `ai-session select|launch`가 v1/v2 registry, Git repository identity, #111 선택 우선순위, post-selection authorization/exclusion, absolute verifier, 10초 timeout, strict 여섯-field verifier result, admission 분류, child env와 `os.execvpe`의 단일 source of truth다. 기존 direct caller는 contract token 없이 v1을 계속 사용할 수 있다. #103 role dispatcher는 `ai-session launch --require-registry-contract role-account-topology-v2 ...`를 반드시 넘기고, `ai-session`은 verifier/provider 전에 v2와 generic multi-account topology를 검증한다. token이 있는데 registry가 v1이거나 필수 alias `codex-default`, `codex-dotfiles`, `claude-default`, `claude-dotfiles` 중 하나, 각 profile의 provider/auth_kind/config-home mode·path 조합/authorization, Claude default/exclusion/binding 중 하나라도 빠지거나 다르면 exit 2 `blocked_contract`다. provider-default mode는 path field를 금지하고 explicit mode는 빈 값이 아닌 안전한 절대 non-symlink home을 요구하며 implicit fallback은 없다. checked-in v2 binding data는 `codex-default`만 Codex default로 참조하고 default/scope/task binding에서 `codex-dotfiles` 참조가 정확히 0이어야 하며, 이 initial policy 위반도 source-contract 검증에서 verifier/provider 전 차단된다. 재사용 launcher는 `codex-dotfiles` binding 금지를 executable에 hard-code하지 않고 유효한 reviewed v2 binding data를 일반적으로 받아들인다. 그러므로 host-local official login과 identity enrollment/admission 준비가 끝난 뒤 default/scope/task binding data만 바꾼 synthetic/future registry도 같은 token으로 통과하며 launcher, role manifest, verifier code, executable 변경이 없다. wrapper는 registry를 parse하거나 topology 판정을 복제하지 않는다. 그 뒤 `ai-session`은 verifier result를 한 번만 parse/classify하여 exit 3의 stable status를 결정하고 strict one-line ### verifier, 실패, credential 경계

- **R6.1** provider verifier는 선택된 account profile의 검증된 home mode 환경에서만 실행한다. Codex adapter는 선택된 `codex-default` 또는 explicit/future binding의 `codex-dotfiles` home에서 `login status`와 redacted `doctor --json`의 separately reviewed official fields만 사용한다. initial unbound candidate의 explicit attempt에서 official login evidence가 없으면 `not_logged_in`으로 provider 전 차단하고 `codex-default`로 fallback하지 않는다. Claude adapter는 `claude-default`에서 R3.4 scrub 뒤 `CLAUDE_CONFIG_DIR`가 없는 exact environment로 official status를 실행하고, `claude-dotfiles`에서만 검증한 explicit separated home을 넣는다. Claude Code 2.1.272의 `claude auth status --help`는 auth status와 JSON/text 출력만 광고하며 공식 usage/quota field 또는 command contract를 제공하지 않는다. Claude adapter는 official auth result가 미로그인이면 `login_status=not_logged_in`과 보수적인 나머지 status를 반환하고, 로그인 상태여도 usage 충분을 추측하지 않고 `usage_status=usage_unknown`을 반환한다. `ai-session`은 전자를 `not_logged_in`으로 먼저 분류하고 후자를 `usage_unknown`으로 분류한다. 따라서 사용자 제공 상태상 `claude-dotfiles`는 future explicit launch에서 `not_logged_in`으로 차단되며 `claude-default`로 fallback하지 않고, login 후에도 separately reviewed official usage adapter가 생기기 전에는 `usage_unknown`으로 차단된다. identity digest의 canonical 대상은 `schema_version=1`, provider, registry의 `auth_kind`, provider adapter가 official status에서 얻은 stable `subject_id`, organization account일 때 stable `tenant_id`(그 밖에는 JSON null) 다섯 field뿐이다. string은 UTF-8 Unicode NFC로 정규화하고 앞뒤 ASCII whitespace를 제거하며 빈 값·control character·NUL을 거부한다. provider/auth_kind는 lowercase, opaque provider ID는 case를 보존한다. JSON key를 Unicode code point 기준 오름차순으로 정렬하고 UTF-8, `ensure_ascii=false`, 공백 없는 `,`/`:` separator로 직렬화한 canonical bytes의 SHA-256 lowercase 64-hex digest를 계산한다. digest file format은 그 64-hex와 단일 LF뿐이다. email/display name/token/path/usage는 입력에 넣지 않는다. provider adapter가 stable subject/tenant field를 제공하지 않으면 추측 없이 unknown identity로 차단한다.

구성은 secret-bearing account home과 non-secret role/settings policy를 교차시키는 두 축이다. account 축은 separate Codex profile 둘과 provider-default/unset·explicit-separated 두 mode의 Claude profile을 선언하되 initial binding policy가 모든 current Codex role/repository를 `codex-default` 하나로 자동 선택하며 role 축과 독립이다. explicit Claude home은 인증뿐 아니라 user settings와 plugin state도 격리하므로 common operational settings는 account home에서 상속하지 않고 reviewed repository content로 복원한다.

1. 여덟 symlink 진입점이 단일 `ai-role-session` dispatcher로 provider와 role을 전달한다.
2. outer dispatcher가 `roles.toml`, Skill/plugin policy, digest-verified common/composed provider settings, reviewed non-secret instruction bytes와 현재 cwd, task/parent/leader 입력을 strict하게 검증해 logical role policy를 만들고, Codex repository-root→cwd project config 또는 Claude account-home/project/local settings를 pre-scan한다. trusted launcher-supplied settings와 untrusted discovered settings는 별도 input class다. role manifest는 account selector 후보나 config-home mode/path를 소유하지 않고 registry를 parse하지 않는다. instruction과 composed settings는 각각 한 번 읽고 hash/version/UTF-8/NUL 또는 strict JSON을 검증한다.
3. global active는 외부 lease proof와 host-local exclusive lock FD를 검증하고 close-on-exec을 해제한다. reviewer/standby는 lock/lease-write/dispatch capability를 받지 않는다. dispatcher는 별도의 one-shot admitted-capability FD도 만든다.
4. outer dispatcher는 자신의 stdin/stdout/stderr를 변경하지 않고 provider 대신 admitted dispatcher phase를 child command로 지정한 `ai-session launch --require-registry-contract role-account-topology-v2`를 subprocess가 아니라 현재 process에서 정확히 한 번 exec한다. `ai-session`이 v2 four-profile topology와 Claude mode/path 조합, reviewed binding data, directory의 Git remote/common-dir와 명시 repository 일치, #111 priority와 최종 exclusion을 검증해 account를 한 번 선택한다. initial binding data에서는 모든 Codex role/context가 `codex-default`, dotfiles source/linked worktree의 Claude role은 explicit `claude-dotfiles`, 그 밖의 Claude role은 provider-default `claude-default`다. `codex-dotfiles`는 explicit 또는 future reviewed binding으로만 선택될 수 있고 unlogged이면 verifier에서 차단된다. R3.4 scrub 뒤 Codex 또는 explicit Claude에는 선택 home 하나만 남기고 default Claude에는 `CLAUDE_CONFIG_DIR`를 재도입하지 않은 environment로 provider verifier를 실행한다. verifier는 shared identity parser로 synthetic/separately reviewed official status output을 메모리에서 parse/redact해 여섯 field JSON만 반환하고, `ai-session`만 result를 admission status로 분류한다. verifier subprocess는 capability/lock FD를 받지 않는다.
5. 실패 시 `ai-session`은 strict status JSON을 inherited stderr에 직접 쓰고 exit 2·3으로 끝난다. 성공 시 같은 stderr에 strict binding JSON을 쓴 뒤 selected child env, unchanged stdio, capability/lock FD로 admitted phase를 exec한다. 별도 outer reader, pipe capture, JSON 재직렬화는 없다.
6. admitted phase는 capability를 정확히 한 번 검증·소비·close한 뒤 trusted common/composed settings의 path/version/hash와 선택 context의 untrusted account-home/project/local settings를 pre-scan한다. trusted target은 exact digest일 때만 허용하고 untrusted policy-affecting/unknown key는 실제 provider 전에 exit 4 JSON으로 차단하며 empty/UI-only `theme` 포함 allowlist만 통과시킨다. 이 검사는 discovered source precedence를 가정하지 않는다. unlogged `claude-dotfiles`는 이 단계 전 `ai-session` admission에서 `not_logged_in`으로 끝나고 다른 Claude profile을 시도하지 않는다. 로그인된 Claude도 current usage adapter 부재로 `usage_unknown`에서 끝나므로 provider가 실행되지 않는다.
7. admitted phase가 provider argv의 필수 override, settings/instruction hash, Skill/plugin/capability set을 manifest와 대조한다. Claude instruction은 검증한 bytes를 decode한 단일 `--append-system-prompt` value이고, settings는 common layer가 이미 병합된 단일 `--settings` document이며 허용 plugin만 local `--plugin-dir`로 전달한다. `--plugin-url`은 없다. 이 argv 대조는 builder 정확성 검사이며 discovered config precedence 증거가 아니다. 일치하면 strict startup JSON을 inherited stderr에 쓰고 실제 interactive provider를 unchanged stdin/stdout/stderr로 exec한다. 이후 stderr와 exit은 provider 소유이고 global provider는 inherited lock FD를 process lifetime 동안 보유한다.

`ai-role-session`은 orchestration runtime, registry parser, account selector, verifier result 분류기를 새로 만들지 않는다. 역할 policy 조합과 config pre-scan/preflight 및 required contract token 전달만 소유하고, v1/v2 parse, Git identity, generic four-profile contract, account 결정·authorization/exclusion·credential environment·exit 2/3 status는 `ai-session`이 계속 소유한다. initial candidate-zero-reference assertion은 reviewed registry binding data와 source test가 소유하며 reusable executable은 future binding을 금지하지 않는다. identity enrollment helper와 verifier는 별도 entrypoint지만 provider-generic canonicalization/parser 구현은 하나를 공유한다. global host-local lock은 중복 process admission만 담당하며 영구 lease generation의 source of truth가 아니다.

## Interfaces and data flow

공통 CLI 형태는 다음과 같다.

```text
ai-codex 또는 ai-claude와 각각의 -orchestrator/-feature-orchestrator/-global-orchestrator 진입점 \
  [--account-profile ALIAS] \
  [--task-id PUBLIC_ID] \
  [--parent-task-id PUBLIC_ID|none] \
  [--binding-file ABSOLUTE_PATH] \
  [--leader-mode active|reviewer|standby] \
  [--leader-scope PUBLIC_SCOPE] \
  [--leader-id PUBLIC_ID] \
  [--lease-proof ABSOLUTE_PATH] \
  [--feature-fallback-contract quality-goal-v1] \
  [--global-effort medium|high] \
  [--verifier ABSOLUTE_PATH] \
  -- [prompt와 policy를 바꾸지 않는 provider argument]
```

`--verifier` 기본값은 provider별 chezmoi target 절대경로로 resolve하지만, 명시값도 반드시 absolute executable regular file이어야 한다. account 선택 context는 기존 `--registry`, repository/organization/directory, task/epic, cost limit을 그대로 전달한다. 사용자 tail은 prompt, image, display 이름처럼 policy-neutral 입력만 허용하고 model/settings/profile/permission/sandbox/add-dir/fallback/resume 관련 option은 거부한다.

role entrypoint의 내부 `ai-session` 호출은 사용자가 완화할 수 없는 `--require-registry-contract role-account-topology-v2`를 포함한다. token 없는 direct `ai-session` caller는 v1 또는 v2의 일반 선택 계약을 사용할 수 있지만 role admission은 four-profile v2 topology만 허용한다. schema v2는 v1 account field에 optional exact `excluded_scopes`를 더하고 allowed scope parser에 `global:*`, Claude account에 mandatory `config_home_mode`을 추가한다. provider-default mode는 path field를 금지하고 explicit mode는 normalization 뒤 절대인 non-symlink path를 요구한다. 빈 문자열이나 implicit fallback은 없다. `global:*`는 `allowed_scopes`에서만 유효하고 `scope_bindings`의 kind는 계속 `repository|organization|directory`뿐이다. explicit/task/scope/default 선택이 끝난 뒤 allowed scope와 exclusion을 차례로 대조하며 exclusion 일치는 항상 거부한다. home-mode validation은 이 priority를 바꾸지 않고 invalid contract를 verifier 전에 차단한다. checked-in binding data는 candidate reference 0을 initial policy로 표현하고 source-contract test가 이를 고정한다. launcher의 generic validator는 로그인·enrollment/admission을 마친 candidate를 가리키도록 reviewed binding data만 바꾼 registry를 실행 코드 변경 없이 수용한다.

`ai-session`은 selection directory에서 Git top-level, absolute common-dir, origin URL을 읽고 GitHub HTTPS/SSH/scp-like URL을 lowercase `owner/name`으로 정규화한다. source checkout과 linked worktree가 같은 common-dir/remote identity를 공유해야 하며 명시 `--repository`와 다르면 차단한다. Git identity가 없을 때만 reviewed canonical directory binding을 fallback으로 쓸 수 있고, identity가 있는데 directory signal과 모순되면 fallback하지 않는다. Codex project config chain은 symlink가 아닌 repository root에서 시작해 cwd까지의 실제 ancestor 각각에서 `.codex/config.toml`을 최대 하나 읽으며 repository 밖의 parent config는 이 검사 범위가 아니다. 빈/comment-only config와 manifest가 명시한 exact UI-only key만 허용하고 policy/unknown key는 차단한다. Claude는 provider-default 또는 explicit account-home의 user settings와 repository root부터 cwd까지의 project/local settings 후보를 검사한다. launcher-supplied composed target과 exact-digest managed common target만 trusted이고, 나머지는 JSON empty object와 manifest의 exact UI-only `$schema`/`spinnerTipsEnabled`/`theme` allowlist만 benign이다. launcher는 한 composed document를 `--settings`로 명시하고 effective-source judgement에 기록하되 `--setting-sources`로 discovered source가 사라지거나 어떤 precedence를 가진다고 가정하지 않는다.

lease proof JSON은 정확히 `schema_version`, `scope`, `leader_id`, `provider`, `generation`, `expires_at`, `direct_parent` field만 가진다. reviewer/standby는 검토 목적으로 읽을 수 있지만 생성·수정하지 않는다. host-local lock key는 정규화한 scope의 SHA-256이며 lock metadata에는 public leader ID, provider, generation, pid, start time만 둔다. lock FD는 provider까지 같은 process의 exec chain에 상속하고 verifier의 별도 subprocess에는 전달하지 않으며 provider 종료 시 kernel이 회수한다.

`ai-session` success binding, role startup, pre-exec failure record는 각각 event별 exact schema의 inherited stderr 한 줄 JSON이다. selection reason은 #111 public text를 사용하고 config home, raw reason, identity와 digest는 넣지 않는다. dispatcher는 `ai-session`을 exec하므로 exit 2/3 failure의 JSON bytes를 capture·parse·재출력하지 않고 같은 FD에 보존하며 별도 status를 만들지 않는다. admission success 뒤 exec되는 admitted phase는 inherited child env와 one-shot capability FD로만 진입하며 capability는 검증 뒤 close되어 provider argv/env/startup record에 전달되지 않는다. stdin/stdout/stderr는 dispatcher 진입부터 provider exec까지 동일 terminal FD를 유지한다. verifier raw stdout/stderr는 verifier subprocess 내부에서 capture·폐기하며 이 subprocess만 stdio/capability/lock 상속의 예외다. provider가 시작되기 전 실패에서는 provider output이 없어야 하고, provider exec 뒤 actual provider stderr는 provider 소유이며 pre-exec public-record 계약과 구분한다.

세 public record는 모두 extra field를 거부하고 `schema_version`은 integer 1, `active_skill_count`는 nonnegative integer, `dispatch_allowed`/`lease_write_allowed`는 boolean, `binding_generation`은 positive integer다. role에 적용되지 않는 startup field는 JSON null, selection 전에 알 수 없는 failure binding field도 JSON null이며 나머지 식별자와 status는 string이다. UTF-8 `ensure_ascii=false`, `sort_keys=true`, compact separator와 단일 trailing LF로 직렬화해 fixture가 bytes까지 비교할 수 있게 한다.

host-local enrollment 인터페이스는 `ai-session-enroll-identity --registry ABSOLUTE_PATH --provider PROVIDER --account-profile PROFILE`이고 profile은 `codex-dotfiles|claude-dotfiles`다. 이는 future explicit apply와 해당 separate home의 interactive login 뒤 별도 운영 단계이고, `codex-default`와 `claude-default` migration에는 호출하지 않는다. helper는 registry로 config home/auth kind를 결정하고 해당 provider official auth status를 한 번 읽어 canonical object의 digest만 mode 0600 파일로 atomic write한다. identity 원문·canonical JSON·digest·config home은 stdout/stderr에 출력하지 않는다. 자동 테스트는 이 entrypoint에 synthetic official output fixture만 주며 실제 login 상태나 account home을 읽지 않고 실제 enrollment를 수행하지 않는다. Codex candidate enrollment 뒤 source activation에는 reviewed registry binding data 외 변경이 없다.

## Failure behavior

- manifest/path/hash/settings schema 오류와 trusted common/composed settings의 digest·merge·role-deny 충돌은 exit 4 `blocked_role_schema` 또는 `blocked_policy`다. 파일을 추측하거나 unreviewed user/account config로 fallback하지 않는다.
- account registry·선택 입력 오류, required token에 대한 v1 또는 nonconforming four-profile v2, checked-in initial binding policy의 `codex-dotfiles` reference, Git explicit/derived/common-dir/directory identity 모순, same-priority profile 충돌과 post-selection exclusion은 verifier 전 exit 2 `blocked_contract`다. initial registry에서 explicit 선택한 unlogged candidate는 topology 오류가 아니라 verifier exit 3 `not_logged_in`이며 더 낮은 priority account를 다시 고르지 않는다.
- Claude provider-default mode의 path 동반, explicit mode의 missing/empty/relative/non-absolute/symlink path는 verifier/provider 전에 exit 2 `blocked_contract`다. default mode는 inherited `CLAUDE_CONFIG_DIR`를 지운 뒤 unset으로만 실행하고 explicit mode에만 검증 path를 재도입하며 mode를 서로 fallback하지 않는다.
- verifier의 미로그인, identity drift, usage unknown/부족, malformed, timeout은 `ai-session`이 기존 exit 3과 strict status JSON으로 중단하며 같은 inherited stderr를 사용한다. unlogged `claude-dotfiles`는 `not_logged_in`이 우선이고 `claude-default`로 fallback하지 않는다. 로그인된 Claude는 official usage adapter가 없으므로 `usage_unknown`이다. 운영자는 해당 Claude launch를 차단 상태로 두고 relogin 반복을 usage 해결책으로 취급하거나 TUI/private endpoint 추론, account/provider 자동 fallback을 하지 않는다. separately reviewed official usage adapter가 요구사항·tests·manifest에 추가된 뒤 새 process로만 다시 시도하며, Codex feature가 필요하면 R2.3의 명시적 대체 계약으로 shared `codex-default`에서 별도 launch한다. provider child는 한 번도 exec하지 않는다.
- installed CLI 부재, compatibility range/version/help option mismatch는 exit 4 `blocked_cli_contract`다. 운영자는 지원 version을 설치하거나 manifest range/test를 명시적으로 개정한다. release gate의 부재는 skip이나 `not_configured`가 아니다.
- sandbox 불가, Codex/Claude untrusted policy-bearing 또는 unknown account-home/project/local setting, trusted settings digest 불일치, policy override tail, high-risk path 요청은 exit 4 `blocked_permission` 또는 `blocked_policy`다. benign allowlist로 추측 확장하거나 `--setting-sources` precedence, unsandboxed 재시도, account-home/settings replication에 의존하지 않는다.
- `codex-dotfiles` 또는 `claude-dotfiles` enrollment digest 누락·mode/type 오류는 `blocked_verifier`, digest 불일치는 `identity_drift`다. verifier는 자동 enrollment/갱신하지 않고 helper 실패도 기존 digest를 교체하지 않는다. initial Codex는 기존 `~/.codex`를 그대로 사용해 relogin하지 않는다. candidate 활성화가 필요하면 별도 home에서 official login과 host-local enrollment/admission 준비 후 reviewed registry binding data만 바꾸고 새 process로 재시도한다.
- global proof/lock 충돌은 exit 4 `blocked_leader_conflict`다. 기존 leader와 generation을 유지하고 reviewer 또는 standby로 자동 강등하지 않는다.
- task/parent/owner/takeover evidence 오류는 exit 4 `blocked_binding`이다. 기존 process/session/binding을 변경하지 않는다.
- provider model unavailable은 provider의 nonzero exit을 그대로 반환한다. 다른 model/provider/account로 자동 대체하지 않으며 운영자가 명시적으로 새 launch를 선택한다.
- instruction/Skill version 변경은 새 process에서만 보인다. 기존 session을 resume하여 강제 갱신하는 복구는 제공하지 않는다.
- 현재 deployed v1 registry와 corrected source v2의 차이는 partial apply로 우회하지 않는다. 두 배포 순서 모두 `blocked_contract`로 멈추고 reviewed v2 registry와 new `ai-session`/role launcher가 함께 future explicit apply된 뒤에만 새 process를 시작한다. deployed old registry의 default/binding은 나중에 안전하게 교체하되 기존 pane의 inherited binding은 유지한다.
- empty 0700 `codex-dotfiles` directory는 오류 복구나 cleanup target이 아니다. 이번 작업은 stat/read/login/delete하지 않고 unlogged candidate home으로 그대로 보존한다. explicit unlogged launch는 verifier로 fail closed하며 future activation은 official interactive login/enrollment/admission 준비와 reviewed registry binding-only source edit로 수행한다.

## Security and risk

account home과 provider output은 민감 trust domain이고 role manifest, account registry, Git identity, lease proof, task ID, account 별칭은 public control data다. public data도 공격자가 바꾸면 권한 상승이나 Claude repository 격리 우회가 가능하므로 strict v1/v2 schema, explicit Claude home mode/path invariant, four-profile required topology token, checked-in initial binding-policy regression, post-selection exclusion, normalized remote/common-dir cross-check, absolute regular-file 검증, symlink 거부, expected hash, owner/mode 검사와 fail-closed preflight를 적용한다. `global:*`는 default authorization에만 쓰고 scope mapping으로 해석하지 않는다. project `.codex/config.toml`, unreviewed Claude account-home/project/local settings, child tail args, inherited env, plugin/MCP catalog는 untrusted policy inputs로 취급한다. inherited env는 R3.4 exact set을 제거한 뒤 선택 Codex home 또는 explicit Claude home만 조건부 재구성하고 Claude default mode에는 config-home 변수를 두지 않는다. reviewed instruction과 common/composed settings는 non-secret만 허용한다.

검증기는 provider output을 부모 stdout/stderr로 relay하지 않고 필요한 상태만 메모리에서 정규화한다. identity는 공개된 canonical field/normalization/SHA-256 계약으로 host-local non-synced digest와 비교하되 raw identity, canonical JSON과 digest를 startup/error/capture에 기록하지 않는다. enrollment helper도 같은 parser를 사용하고 두 dotfiles candidate에만 digest를 owner-only atomic file로 저장한다. authentication file은 어떤 profile 사이에도 copy/sync/snapshot/symlink하지 않는다. 테스트는 synthetic marker만 사용하며 실제 account home과 prepared candidate directory를 열거나 enrollment를 수행하지 않고 현재 pane을 변경하지 않는다.

legacy Codex sandbox와 beta permission profile 혼합, discovered setting의 우선순위 불확실성, Claude sandbox fallback, account-home 분리에 따른 hooks/plugins 누락, global reviewer의 multi-agent/dispatch, unrestricted 개인 Mac launcher가 가장 큰 권한 위험이다. 신뢰 가능한 effective-config/dry probe가 없는 부분은 untrusted policy-bearing/unknown config를 pre-scan 차단하고, digest-verified single composed settings, 명시 CLI, OS read-only sandbox, tool/Skill/plugin deny, strict MCP policy를 중첩한다. common `env`와 plugin은 role deny 및 R3.4 scrub을 통과해야 하므로 hooks 복원이 reviewer/standby dispatch·lease-write나 고위험 경로를 다시 열지 않는다. launcher 자체 argv self-compare는 외부 config 차단의 증거로 취급하지 않는다.

## Test strategy

단위 테스트는 v1/v2 registry와 generic four-profile required topology, Claude provider-default/unset·explicit-home schema invariant, initial Codex candidate zero binding references, manifest/common/composed-settings schema와 hash, Git remote/common-dir identity, post-selection exclusion, trusted/untrusted config-chain pre-scan, command builder, exact env scrub, supported additive instruction value/hash, atomic mode, status precedence/exit/inherited-stderr를 직접 검사한다. integration test는 fake provider/verifier와 temp two-Codex/two-Claude homes를 사용해 default Claude variable absence와 explicit exact path, initial default-only matrix, explicit unlogged candidate fail-close, fake login/enrollment/admission 뒤 binding-only activation과 실제 `exec` 경계까지 capture하되 PTY fixture로 stdin/stdout/stderr의 `isatty`, FD target, device/inode가 dispatcher 전후 동일함을 확인한다. effective-setting-sources fixture는 명시된 one composed document, managed common digest와 local plugin만 trusted임을 판정하고 unreviewed source 또는 `--setting-sources` precedence에 의존하지 않음을 검사한다. fake `workmux` smoke는 separated profile에서도 waiting/working/done hook이 호출되어 status observability가 복원됨을 검사한다. 고위험 E2E는 Codex initial/future matrix와 role-policy byte identity, dotfiles source/linked worktree/non-dotfiles Claude mode matrix, explicit wrong Claude profile, invalid mode/path, v1/v2 partial deployment 양방향, hostile/benign-theme Codex·Claude config, Claude `not_logged_in`→`usage_unknown` precedence, common env/plugin deny와 concurrent active provider의 lock-FD lifetime을 포함하고 network를 차단한다. credential/account-home copy/symlink, network plugin fetch, current-pane/session/process mutation, real candidate-directory access는 failing sentinel로 감시한다. portable test는 CLI metadata fixture만, 이 Mac release gate만 installed `--version`/`--help`를 사용한다. source-target 검사는 chezmoi source를 fixture home에 render한 결과와 expected target mode/content/symlink를 비교하며 실제 home과 `chezmoi apply`를 사용하지 않는다.

## Decisions

### D1. role 설정 배치와 합성 방식

| 안 | #111 독립축 | project override 방지 | chezmoi 배포 | 인증정보 비복제 | 결론 |
|---|---|---|---|---|---|
| (a) account home마다 role config 복제 | role과 account 수의 곱으로 설정이 결합된다 | 각 copy를 검증해야 해 drift 가능성이 높다 | target 생성 수가 늘고 삭제/갱신이 복잡하다 | config와 auth home 경계가 섞여 credential copy 유혹이 생긴다 | 기각 |
| (b) 외부 role manifest를 launcher가 읽고 CLI/settings override로 강제 | role과 account를 런타임에 직교 결합한다 | 필수값을 최종 argv와 config pre-scan에서 고정한다 | non-secret manifest/settings/prompt만 한 번 배포한다 | account home에는 손대지 않는다 | 선택 |
| (c) role×account 합성 profile을 미리 생성 | 가능한 조합마다 새 identity가 생겨 #111 selector 의미가 흐려진다 | 생성기는 강제할 수 있으나 조합 drift가 남는다 | 조합 폭발과 host별 재생성이 필요하다 | 합성 target이 auth home을 참조·복제할 위험이 있다 | 기각 |

선택안 (b)는 #111의 selector/verifier 우선순위를 유지하고 role policy만 외부에서 더한다. Codex는 separate account home 둘을 선언하지만 initial binding data가 모든 role/repository를 기존 `~/.codex`의 `codex-default`로 보내며 role별 auth home을 만들지 않는다. future candidate 선택도 account binding만 바뀌고 role policy는 그대로다. Codex named `--profile`은 선택 account의 `CODEX_HOME` 안 파일을 요구하므로 authoritative 강제 수단으로 쓰지 않고, logical profile ID와 최종 `-c`/flag를 사용한다. Claude는 account home마다 설정을 상속·복제하지 않고 secret-free common source와 role settings를 chezmoi render 때 하나로 구조 병합한다. launcher는 그 reviewed bytes를 read-once/hash 검증해 단일 `--settings`로, reviewed local plugin만 `--plugin-dir`로, instruction UTF-8 값은 지원되는 `--append-system-prompt`로 전달한다. 설치 help에 없는 file flag, network `--plugin-url`, prompt 파일 경로를 provider에 전달하지 않는다.

### D2. Codex permission engine

이번 구현은 검증된 legacy sandbox chain만 사용한다. 설치본이 beta permission profile을 제공하더라도 legacy와 합성하지 않는다. reviewer/standby의 read-only와 multi-agent/plugin/MCP 제거를 함께 검증한다. beta 전환은 모든 legacy key를 제거하고 별도 migration으로 검증할 때만 가능하다.

### D3. global leader admission

영구 lease 저장소를 새로 만들지 않고 외부 lease proof 검증과 host-local exclusive process lock을 조합한다. lock FD는 verifier subprocess에서 닫고 dispatcher부터 provider까지 하나의 exec chain에 상속하여 kernel lifetime으로 소유권을 유지한다. 이는 #94/#98/#99의 generation source of truth를 침범하지 않으면서 같은 host 중복 active를 실제로 막고, cross-host 단일 leader는 외부 proof issuer의 한-owner 계약에 의존한다. reviewer/standby는 proof를 읽을 수만 있고 발급·갱신하지 않는다.

### D4. verifier의 공식 usage 경계

공식 status 명령의 separately reviewed machine-readable contract에서 login/identity/usage를 확인할 수 있는 값만 admission 근거로 인정한다. 현재 설치된 Claude Code 2.1.272의 `claude auth status --help`는 auth status와 JSON/text 출력만 광고하고 usage/quota contract는 없다. official auth result가 미로그인을 입증하면 verifier는 이를 보존하고 `ai-session`은 `not_logged_in`을 usage보다 먼저 분류한다. 로그인 상태에서는 usage를 추측하지 않고 `usage_unknown`으로 차단한다. 따라서 user-reported unlogged `claude-dotfiles`의 future launch 기대 status는 `not_logged_in`이며 `claude-default`로 fallback하지 않는다. login 후에도 CLI release gate 통과나 login 자체가 usage 결과를 바꾸지 않는다. 운영자는 launcher를 차단 상태로 두고 relogin 반복을 usage 복구로 취급하거나 TUI scraping, private endpoint, raw output relay, consumer account/provider/model 자동 전환을 하지 않는다. separately reviewed official usage adapter가 별도 요구사항·tests·manifest로 추가된 뒤 새 process에서만 재시도한다. 운영자가 Codex feature 대체를 택하면 shared `codex-default`를 쓰는 R2.3의 명시적 별도 launch여야 한다.

### D5. 기존 full_auto 처리

기준 revision의 `private_full_auto.config.toml`은 실행 호출처가 없고 이름과 달리 `on-request/workspace-write`다. 삭제나 역할 profile 이관은 기존 수동 사용을 불필요하게 깨뜨릴 수 있으므로 byte-for-byte 유지하되 deprecated compatibility artifact로 문서화하고 새 role manifest에서는 참조를 금지한다.

### D6. 신뢰 가능한 effective-config probe가 없는 provider 설정

| 안 | 보안 근거 | 호환성 | 결론 |
|---|---|---|---|
| (a) launcher가 만든 expected argv와 fake child capture를 비교 | builder 자체만 확인하며 실제 provider config precedence를 증명하지 못한다 | 넓지만 동어반복이다 | 기각 |
| (b) `--setting-sources ""`나 CLI override가 우선한다고 help만으로 가정 | flag 존재만 확인하고 의미 동작을 확인하지 못한다 | 조용한 약화 가능성이 있다 | 기각 |
| (c) digest-verified launcher-composed settings를 별도 trusted input으로 전달하고 unreviewed account-home/project/local config의 policy/unknown key를 pre-scan 차단 | explicit document로 common settings를 복원하면서 discovered-source precedence는 가정하지 않고 provider 실행 전에 fail closed한다 | empty와 `$schema`/`spinnerTipsEnabled`/`theme`만 untrusted benign input으로 허용한다 | 선택 |

Codex는 repository root→cwd `.codex/config.toml`, Claude는 적용 가능한 account-home/project/local settings를 각각 검사한다. Claude launcher가 pass하는 common+role single document와 provider-default home의 managed common target은 exact path/version/digest가 맞을 때만 trusted이고, 그 외 discovered source에는 기존 policy-key 차단을 적용한다. `--setting-sources`가 어떤 source를 제거하거나 어떤 precedence를 만든다고 가정하지 않으며 explicit composed document만 복원 근거다. 향후 인증·network 없는 공식 effective-config/dry probe가 확인되면 별도 Spec에서 차단 범위를 줄일 수 있지만 이번 revision은 (c)를 고정한다.

### D7. CLI compatibility와 release evidence

### D8. identity enrollment와 digest 재현성

|---|---|---|---|
| (a) 운영자가 raw ID를 복사해 수동으로 hash | shell history/stdout에 identity가 남을 수 있다 | 절차 drift가 크다 | 기각 |
| (b) verifier가 첫 실행 identity를 자동 등록 | 편리하지만 공격 시점 identity를 신뢰해 fail-open된다 | 자동이지만 안전하지 않다 | 기각 |
| (c) host-local helper와 verifier가 공개 canonical contract의 shared parser를 사용 | raw identity를 출력하지 않고 digest만 0600 atomic write한다 | 공식 status가 있는 host에서 결정적으로 재현된다 | 선택 |

helper는 future explicit apply와 해당 separate home의 interactive login 뒤 운영자가 `codex-dotfiles` 또는 `claude-dotfiles`에 명시 호출할 때만 enrollment를 수행하고 verifier는 파일을 생성·갱신하지 않는다. existing `codex-default`와 `claude-default`는 이번 migration enrollment 대상이 아니다. 자동 검증은 synthetic provider output과 temp home만 사용한다.

### D9. interactive stdio와 global lock 소유

| 안 | TTY 보존 | public record 검증 | lock lifetime | 결론 |
|---|---|---|---|---|
| (a) outer process가 `ai-session` stderr를 pipe로 capture하고 provider output까지 relay | provider TUI의 fd/terminal ownership을 바꿀 수 있다 | outer가 parse 가능하지만 provider stderr와 경계가 섞인다 | outer lifetime에 의존한다 | 기각 |
| (b) outer process가 PTY proxy가 되어 양방향 relay | 구현·signal/window-size forwarding이 복잡하고 byte transparency 증명이 어렵다 | 가능하지만 새 terminal owner가 된다 | proxy lifetime에 의존한다 | 기각 |
